Besart's Logbook

Week 11

Tasks Completed

Elevator Request Interface Development

This week I updated the elevator control webpage so that the floor request buttons could communicate with the backend system. The original static buttons were modified to include data attributes identifying the requested floor and the controller responsible for sending the request.

Separate button groups were created for floor-controller requests and car-controller requests. Each button now provides the JavaScript code with the information required to generate the correct request without requiring a separate event handler for every button.

JavaScript Fetch API Implementation

I developed the elevatorControl.js component to detect button presses and send floor requests to the PHP backend. The JavaScript reads the requested floor and controller type from the button's data and sends the information as JSON using an asynchronous POST request.

The script also disables the floor request buttons while a request is being processed. This prevents duplicate submissions caused by repeated button presses. Once the server responds, the webpage displays either a successful confirmation message or a description of the error that occurred.

PHP Request Endpoint Development

I created the request-floor.php to receive and process requests submitted by the elevator control webpage. The endpoint confirms that the user is logged in, verifies that the request uses the POST method, and decodes the JSON information sent by the JavaScript component.

This validates that the requested floor is between floors one and three and confirms that the request originated from either a floor controller or the car controller. It then reads the latest elevator position from the database and prepares a new CAN transaction for storage.

Database Troubleshooting

A significant portion of this week's work involved troubleshooting the connection between the PHP endpoint and the MySQL database. The initial database INSERT statement attempted to use a column named sent. Testing showed that this column did not exist in the can_transaction table, and the correct column name was sent_by.

After correcting the column name, another error occurred because the code attempted to insert the text value floor_controller into the sent_by column. Inspection of the database structure showed that this column uses the BIGINT data type and therefore requires a numeric value.

Further testing revealed that sent_by is a foreign key referencing the can_id column in the can_node table. This meant that the value could not be a user ID or an arbitrary controller number. It had to match an existing CAN node identifier.

CAN Node Mapping

I inspected the can_node table using phpMyAdmin and identified the valid CAN node identifiers used by the system. These included the car controller and each of the three floor controllers.

The backend logic was updated so that car-controller requests use CAN ID 512. Floor-controller requests use CAN ID 513 for floor one, CAN ID 514 for floor two, and CAN ID 515 for floor three. This change ensures that every value inserted into sent_by satisfies the database foreign key constraint.

Browser Debugging

I used the browser developer tools to identify client-side errors and inspect communication between the webpage and the PHP endpoint. One of the first errors occurred because the JavaScript attempted to update an element with the ID request-status, but that element did not exist in the webpage.

I added the missing status element to member.php, allowing the JavaScript to display progress, success, and failure messages.

Database Error Handling

The PHP endpoint was configured to return structured JSON responses for both successful and unsuccessful requests. Separate error handling was included for invalid JSON, invalid user input, database failures, and unexpected server errors.

Returning the database error information during development made it possible to identify problems involving incorrect column names, invalid data types, and foreign key constraint violations. This provided a more efficient troubleshooting process than relying only on whether the database appeared to update.

Challenges

The main challenge this week was understanding how the existing database tables were related. As one of the group members had created the database structure, I was not familiar with the relationships between the tables and the purpose of each column.

Another challenge was determining whether failures originated in the HTML interface, JavaScript code, PHP, or database structure. The problem had to be separated into individual stages and tested one stage at a time.

What I Learned

This week I gained practical experience integrating an HTML and JavaScript frontend with a PHP and MySQL backend. I improved my understanding of JSON requests, the Fetch API, prepared SQL statements, session validation, and structured server responses.

I also developed a stronger understanding of relational database design. In particular, I learned how foreign keys restrict the values that can be inserted into a table and how related tables must be inspected before deciding what information should be stored.

The troubleshooting process reinforced the importance of reading complete error messages. Each error identified a different layer of the problem and helped guide the next correction.
