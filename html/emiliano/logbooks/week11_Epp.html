Week 11

Overview and Objectives

The work carried out during Week 11 closes out the Phase II individual deliverables for the Supervisory Controller (SC). The SC is the Raspberry Pi node that bridges the local-area network and the CAN network: it receives floor requests, runs a finite-state machine, and commands the Elevator Controller (EC) over CAN ID 0x100.

Four topics were delivered on top of a single shared finite-state machine core, so that all three operating modes reuse the same hardware-validated movement, queueing, arrival, and audio code. The modes differ only in which messages they accept. The topics delivered were Sabbath Mode, Floor-Arrival Audio, Maintenance Lockout, and CAN ↔ Database communication.

The finite-state machine runs at (a 200 ms sleep per loop). On every iteration it polls the CAN bus for one frame, logs that frame to the database, applies it to the state machine, then advances the machine and mirrors the resulting state back to the database.

The Baseline ; FSM States and Priority Queues

The shared core of the supervisory controller consists of four states and three priority queues. Each operating mode acts upon this same structure, supplying its own inputs and its own message filter.

States

The four states of the machine are STATE_FLOOR1 = 0, STATE_FLOOR2 = 1, STATE_FLOOR3 = 2, and STATE_MOVING = 3.

Load-bearing convention. The zero-based numbering matters throughout the implementation: floor = (int)state + 1 and state = (ElevatorSate)(floor − 1). Both conversions appear repeatedly across the source file.

Request queues ; strict priority

Requests are held in three queues, which the scheduler examines in a strict order of precedence.

Priority Queue Source CAN ID
1 (highest)carQueueIn-car buttons (Car Controller)0x200
2floorQueueHall-call buttons (Floor Controllers)0x201–0x203
3 (lowest)websiteQueueRequests from the web interface (via database);

The scheduler, fsmPeekPriotity(), scans the car queue, then the floor queue, then the website queue, and returns the first entry that is not the current floor. A website request therefore only wins when no physical button press is pending.

Sequence of elevator commands (normal mode)

  • Door the door is reported OPEN and then CLOSED by the Car Controller.
  • Listen a five-second window collects all requests while the car is stopped (REQUEST_COLLECTION_SEC).
  • Select the collected requests are priority-sorted and a target is chosen.
  • Wait a five-second pre-move delay elapses after the door is closed (PRE_MOVE_DELAY_SEC).
  • Command the supervisory controller transmits a go-to-floor command to the Elevator Controller on ID 0x100, and the state becomes MOVING.
  • Arrive the machine waits for the arrival confirmation from the Elevator Controller, or for an eight-second fallback timer, and then calls fsmArrive().
  • Update the database is updated, the arrival audio is played, and the cycle repeats.

Topic 1 ; Sabbath Mode

autonomous cycle no user input parallel run loop ~260 new lines

Sabbath Mode moves the car autonomously through every floor, opening its doors at each stop, so that no passenger is ever required to press a button. It runs an endless shuttle cycle in a parallel loop, so the normal finite-state machine is never broken.

The cycle

The car follows an indefinite 1 → 2 → 3 → 2 → 1 → … shuttle, never a 1 → 2 → 3 → 1 wrap. The door opens at every stop for five seconds, then closes and the car departs, so that no floor is ever skipped. Floor targets are generated automatically by sabbathMove() according to the following rules.

  • At floor 1, always travel to floor 2.
  • At floor 2, travel to floor 3 if the car came from floor 1; otherwise travel to floor 1.
  • At floor 3, always travel downwards (to floor 2 if the car came from floor 2, otherwise to floor 1).

Reuse of fsmArrive()

sabbathArrive() clamps an invalid floor to 1 and then calls the shared fsmArrive(), thereby inheriting the same database write, echo suppression, queue purge, and audio announcement. It subsequently overrides doorClosed back to DOOR_OPEN, because Sabbath Mode holds the door open at every floor. Only a minor change to the elevator structure (the door status field) was required.

The message filter

The filter that gives the mode its "ignores everything" behaviour is a single guard clause.


if (id != ID_EC_TO_ALL || fsm->state != STATE_MOVING) return;

All requests are still logged to the database first and only then ignored: Sabbath Mode obeys no requests, following only its fixed cycle. It listens solely for the arrival confirmation issued by the Elevator Controller while the car is moving, and it never polls the website.

Server-side button lock. When Sabbath Mode is selected, nothing on the website appears available ; the request controls are locked out.

Topic 2 ; Floor-Arrival Audio

accessibility every mode non-blocking ~160 new lines

On arrival at any floor, in every operating mode, the Raspberry Pi plays a two-part sound as an accessibility feature: a ding chime, a gap of 120 ms, and then the spoken floor number.

How it works

  • miniaudio ; a public-domain, single-header library, vendored by means of a single #define. It requires no Makefile entries and no apt packages.
  • All clips are decoded into memory at initialisation, so that arrival playback incurs no file input/output and no MP3 decoding inside the real-time loop.
  • The ding and the voice clip are scheduled on the engine's PCM clock, so no sleep() call is required; playback occurs on a dedicated background audio thread.

Why it is designed this way

  • Exactly one code path produces an arrival, namely fsmArrive(), so the guarantee that "every arrival announces" is structurally true rather than merely observed.
  • The path is non-blocking: a blocking ding–sleep–voice sequence would stall the loop for approximately two seconds and risk dropping CAN frames.
  • Playback runs on a dedicated thread, so the main thread is never locked.
Safeguards ; degrade, never drop. If no audio hardware is present, the elevator simply runs silently. If the ding asset is missing, the announcement downgrades to the floor number alone. The ding is optional, serving as an attention-getter, whereas the voice is mandatory, being the real indicator. The whole audio path can be tested in isolation.

Topic 3 ; Maintenance Lockout

digital e-stop filter at ingestion website = sole control ~130 new lines

Maintenance Lockout is a digital emergency stop. Every physical input is filtered out, although it is still logged, while an authenticated user retains full control from the website, which becomes the only channel capable of moving the car. The whole mode lives in one function, maintenanceProcessMessage(), which divides incoming frames into commands, which are dropped, and telemetry, which is honoured.

Commands ; dropped

  • Physical floor buttons (F1, F2, F3 on 0x201–0x203).
  • In-car floor buttons (0x200 carrying a floor payload).

Telemetry ; kept

  • Door state (0x200 with a floor byte of 0), so that the machine continues to know the real door state.
  • Arrival confirmations from the Elevator Controller (0x101), so that the model never drifts.

Because no hardware request can reach a queue, the only route by which anything can be queued is fsmPollWebsite() writing into websiteQueue. It follows that the elevator moves on website requests alone. Movement, queueing, arrival, and audio all reuse the identical hardware-validated code employed in normal mode, amounting to approximately 100 lines of reused core. The control channel already sits behind an authenticated user session, so every command carries a real identity.

Honest limitation. This is a software lockout that complements, and never replaces, a hardware emergency stop. On entry it deliberately does not command a move, unlike normal and Sabbath modes, which send a go-to-floor-1 frame on entry: a digital emergency stop must not command motion at the instant it is engaged.

Topic 4 ; CAN ↔ Database Communication

bidirectional bridge MariaDB prepared statements ~700 new lines

This topic delivers the bidirectional bridge between the real-time CAN bus and MariaDB. It unifies the firmware, the database, and the web interface into a single system, with the database acting as the integration bus between two processes, two languages, and two lifecycles.

CAN to database ; the telemetry and audit path

The path proceeds from sensing a frame, to decoding it, to logging it, and finally to updating the position record only when it changes. Every CAN frame present on the bus is decoded using the same decoders as the console, written to can_transaction in both raw and textual form, and elevator_position is updated only when the state actually changes, giving an append-only, publish-on-change record.

Database to CAN ; the command round trip

The round trip proceeds from a click on the web interface, through validation, to the polling performed by the firmware, to the transmission from the supervisory controller to the Elevator Controller, and finally to arrival. In detail, member.php posts JSON to request-floor.php, which runs six checks and produces a priority-3 entry in websiteQueue; the finite-state machine then emits a frame to the Elevator Controller, and the result reported by the Elevator Controller and supervisory controller is written back to the database. Floor input is validated, whitelisted to the set {1, 2, 3}, and bound by means of prepared statements before it reaches the database.

Write on change. The supervisory controller writes to the database once the state or the position of the elevator has changed, rather than on a fixed schedule.

Cross-Cutting Practice ; One FSM, Three Modes, Three Filters

The three operating modes are distinguished not by their mechanism but by the filter applied at the point at which messages are ingested.

Mode Message handler Accepts
NormalfsmProcessMessage()Everything
SabbathsabbathProcessMessages()Only arrivals from the Elevator Controller
MaintenancemaintenanceProcessMessage()Only website input, together with telemetry

Four recurring principles

  • One chokepoint per concern ; one arrival function, one connection accessor, and one filter per mode.
  • Same mechanism, different filters ; the modes differ only in the messages they accept, with one shared, hardware-validated mechanism underneath.
  • Degrade, never drop ; no missing file, unreachable database, or dropped frame can stop the elevator, since each failure has a lesser fallback mode.
  • Observe everything, act selectively ; logging always precedes filtering, so that the record reflects reality and the filter decides only what is acted upon.

FSM Function Reference ; fsmFunctions.cpp

The finite-state machine is the brain of the supervisory controller. On every 5 Hz iteration it polls the CAN bus for one frame, logs that frame to the database, applies it to the state machine, and then advances the machine and mirrors the resulting state to the database. The three run modes ; fsmRun(), sabbathRun(), and maintenanceRun() ; are built from the same parts.

Initialisation and helpers

  • fsmInit() ; performs the cold start: the state is set to FLOOR1, all queues are emptied, the floor fields are set to 1, and the mode is set to "elevator". It seeds the pub* snapshot with impossible sentinel values (−1 or NULL) so that the very first call to fsmPublishPosition() always writes a row, allowing the website to learn the new mode immediately rather than waiting for the first floor change.
  • queueContainsFloor() ; walks a copy of a queue. It is used before every push, so that a held button, a repeated frame, or a repeated database value does not queue the same floor ten times.
  • purgeFloorFromQueue() ; rebuilds a queue without a given floor, since std::queue provides no random-access erase operation.
  • fsmConsumeRequestsForFloor() ; purges a floor from all three queues at once, expressing the rule that once a floor is served, or merely locked in, every pending request for it is satisfied.
  • fsmPeekPriotity() ; the scheduler. It scans the car, floor, and website queues on copies and returns the first entry that differs from the current floor, or 0. Peeking never consumes.

State and database bridge

  • fsmFloorPair() ; the single source of truth for the (current, last) pair that both website tables expect. While the car is MOVING, current = targetFloor, that is the destination, and is_moving = 1 informs the website that the car has not yet arrived; otherwise current = state + 1. Both the publisher and the CAN logger call this function, so they can never disagree.
  • fsmPublishPosition() [SC → DB] ; mirrors the live state into elevator_position. Change detection is applied: if the floor, last floor, moving flag, door-closed flag, and mode all match the pub* snapshot, the function returns without touching the database, since otherwise the 5 Hz loop would insert approximately 300 identical rows per minute. On a failed insert the snapshot is left untouched, so that the next tick retries and nothing is silently lost.
  • fsmLogRxMessage() [SC → DB] ; records one received frame into can_transaction, and is called before the mode handler in every mode. The principle is that sensed means sensed: discarded frames nonetheless existed on the bus, so the log constitutes a bus trace rather than an action trace. A foreign-key guard skips unregistered senders instead of throwing. Only received frames are logged; the controller's own transmissions (id 256) are not.
  • fsmArrive() [SC → DB] ; the single arrival hook shared by all modes. It sets the stationary state, marks the door closed, clears the served floor from all queues, calls db_setFloorNum(floor), records lastDbfloor = floor as the anti-echo pairing, and fires audioPlayFloor() on its own thread. It does not publish directly; the call to fsmStep() at the end of the same loop performs the publication.

The step functions

fsmStepInner() constitutes one evaluation tick and contains six early return paths, covering the cases of waiting on the door, waiting on the pre-move delay, and still collecting requests. When the car is not moving, the function proceeds as follows: if the door is open, the current floor is served; if a target is already locked, the five-second pre-move delay is awaited and the car then departs, transmitting by means of the persistent non-blocking pcanFsmTx rather than the blocking pcanTx; if the door has just closed, the five-second listening window is opened; if the window is open, requests continue to be gathered; and if the window has expired, the next target is selected by priority and locked. While the car is MOVING, an arrival normally arrives from the Elevator Controller on 0x101, but an eight-second fallback timer calls fsmArrive() regardless, so that the machine can never stick in the MOVING state.

Why fsmStep() wraps fsmStepInner(). fsmStep() is simply fsmStepInner() followed by fsmPublishPosition(). Because the inner function contains six early returns, placing the publication inside it would skip publishing on most paths. The wrapper guarantees that every transition ; arrival, departure, door opening or closing, and mode entry ; is mirrored to the database exactly once per loop.

Mode-specific run loops

All three loops share a common skeleton: standard output is unbuffered, the CAN channel is opened and the program aborts if it cannot be opened, audio is initialised on a non-fatal basis, fsmInit() is called, fsm.mode is set, db_setFloorNum(1) is issued, a single publication is performed so that the mode is recorded the instant it is selected, the SIGINT handler is installed, and the loop then runs at 5 Hz, polling, logging, processing, and stepping. Maintenance mode differs in three respects: the mode string is "maintenance", the door is forced OPEN, and no go-to-floor-1 frame is transmitted on entry. The database connection is opened once by main.cpp through db_open() and thereafter reused; the run loops never open or close it.

Supervisory Controller ↔ Database Communication

Transport is provided by MySQL Connector/C++ over tcp://127.0.0.1:3306, against the schema elevator. One shared connection is reused by every call; db_conn() reconnects should MariaDB have restarted, and every function catches its own SQLException and returns −1, so that nothing throws into the finite-state machine. An uncaught exception would otherwise kill the firmware mid-run.

The traffic is deliberately asymmetric. The path from the supervisory controller to the database is heavy, carrying every frame sensed, every state change, and every arrival. The path from the database to the supervisory controller is a single value, namely elevatorNetwork.currentFloor, read once per second by fsmPollWebsite(). That value is the only means by which the database can influence the controller.

fsmPollWebsite() ; the one inbound channel [DB → SC]

  1. The function is rate-limited to once per second, since the 5 Hz loop would otherwise query MariaDB five times a second.
  2. It reads SELECT currentFloor FROM elevatorNetwork WHERE nodeID = 1.
  3. It rejects any value below 1 or above 3. This single check covers both the case in which the database is down, which returns −1, and the case in which the database holds garbage. The machine continues to run normally with the database offline.
  4. Echo suppression: if the value equals lastDbfloor, the function returns. The controller writes this same column on every arrival, so without this test it would read back its own write and re-queue the floor at which it had just arrived, indefinitely.
  5. Otherwise it remembers the value and pushes it onto websiteQueue, with deduplication applied.

What the database can change: it can add a lowest-priority destination, which becomes a real target once no car or floor button is pending; and in Maintenance Mode it is the only thing that can move the car. What it cannot change: the operating mode, which is set only by the firmware menu; the door; and the queue priority. Nor can it cancel a request or crash the controller, since every read is bounds-checked and every error is caught.

Conclusion

Four topics and three operating modes were delivered on one shared finite-state machine core over approximately two weeks, amounting to some 1,840 lines of C++ across 6 firmware modules and more than 14 changed files. The design holds to four principles throughout ; one chokepoint per concern, one mechanism with different filters, graceful degradation, and observe-everything while acting selectively ; and it is these principles that allowed three markedly different behaviours to reuse a single hardware-validated code path.
