Emiliano's Logbook

Week 13

Overview

The main effort this week was the unique feature for the final deliverable: camera based hand gesture control of the elevator. Holding up 1, 2 or 3 fingers in front of the Raspberry Pi Camera now sends a floor request to that floor. The detection pipeline was brought up from scratch, four separate bugs were found and fixed, and the feature was tested end to end on the real elevator.

Tasks Completed

  1. Brought up the MediaPipe Hand Landmarker detector on the Pi:
    • Patched the Google sample so it no longer imports the removed mediapipe.solutions module. Landmarks are now drawn manually with OpenCV using HandLandmarksConnections.
    • Replaced cv2.VideoCapture() with Picamera2, because the Camera Module 3 is libcamera only and OpenCV cannot see it.
    • Validated the pipeline end to end: 21 landmarks tracking correctly at 22.8 fps inference on 1280x960.
  2. Evaluated the Hailo-8L AI accelerator and decided not to use it:
    • Measured the real CPU cost of the detector: the system goes from 0.13 to 1.04 busy cores, so the detector uses about 0.9 of the 4 available cores. Three cores stay free and the supervisor loop is a 5 Hz poll that is essentially idle, so there is no CPU shortage to fix.
    • The Hailo Dataflow Compiler only runs on x86_64 Ubuntu, so the model cannot be compiled on the Pi at all.
    • MediaPipe Hands is a two stage graph (palm detection, then crop and rotate, then landmark regression). Only the landmark half exists as a prebuilt HEF, so the rest would have to be reimplemented by hand.
    • Conclusion: days of work to free 0.9 cores that are not needed. Documented as a measured engineering decision.
  3. Wrote python/gestureRecognition.py - finger counting and debouncing:
    • Counts extended fingers from the 21 landmarks. The thumb is deliberately ignored, which also removes any dependence on handedness.
    • Uses a rotation invariant test (distance from the wrist to the tip against wrist to the PIP joint) instead of the common tip.y < pip.y comparison.
    • A GestureLatch debounces the per frame count down to one request per gesture, using the same idea as the STM32 pushbutton flag: hold steady for 15 frames to fire once, then the hand must be withdrawn plus a 3 second cooldown before it can fire again. A drift check rejects a hand that is only sweeping past the camera.
  4. Wrote python/elevatorRequest.py - the link to the elevator:
    • Inserts the request into can_transaction as sent_by = 768, data = floor, which is exactly what the website car controller button already writes. This means the supervisor picks it up within 300 ms with zero firmware changes and no rebuild.
    • The message column is tagged "Gesture control requested floor N" so gesture requests are still distinguishable in the logs.
    • The insert runs on a background worker thread, because a blocking database call inside a 22 fps loop would stall the video. Measured at 0.0007 ms per call from the loop's side.
    • Added PyMySQL to requirements.txt. It is pure Python, so unlike a compiled driver it cannot be shadowed by a binary incompatible system copy.
  5. Integrated both modules into detect.py with a small on screen display showing the live finger count, the armed or latched state, and the last request sent.
  6. Tested the feature at every level:
    • Rotation invariance proved with synthetic hands rotated through 0, 30, 45, 90, 180 and 270 degrees.
    • Six debounce cases checked, including a single fire on a long hold and no fire while waving.
    • Database write verified against the real table.
    • Full end to end run on the elevator - working.

Challenges

  1. Picamera2 would not import inside the virtual environment. It failed with "numpy.dtype size changed, may indicate binary incompatibility". The cause was that the venv uses --system-site-packages so that picamera2 is visible, but MediaPipe pulls numpy 2.x into the venv while the system simplejpeg was compiled against numpy 1.24. Fixed by pinning simplejpeg>=1.9.0 so a numpy 2 compatible copy is installed inside the venv. Reinstalling picamera2 through apt does not help, because the system package was never the problem.
  2. The camera colour format names are misleading. Skin tones looked wrong and hand detection was unreliable. Picamera2's format names are byte reversed: asking for 'BGR888' actually returns an RGB array. The original code was therefore feeding MediaPipe images with red and blue swapped. Confirmed by measuring against an rpicam-jpeg reference on saturated pixels, since a low colour scene makes a channel swap almost invisible by eye. Fixed by using 'RGB888'.
  3. The Left and Right hand labels were reversed. MediaPipe assumes the input image is already mirrored, and the preview is mirrored with cv2.flip so the operator's hand moves the right way on screen. Fixed by swapping the label in code rather than removing the flip, which would have made the preview unusable.
  4. The debounce could latch up. Re-arming originally required the hand to be withdrawn and the cooldown to expire at the same moment, so lowering and raising the hand during the cooldown left it stuck until the hand was lowered a second time. Fixed by remembering that a release happened, so a release during the cooldown still counts.
  5. Sabbath mode silently swallows gesture requests. Not a bug, but it cost time during testing. The mode has to be set back to elevator before any gesture will move the car.

Debugging the Elevator Limit Sensor

During one of the testing sessions the elevator Overshoot itself all the way to the top of the Elevator messing up the "limit Switch" IR light detectors These detectors need to be fully inline with each other to not be triggered. However, since they were out of position. The Servo controler of the elevator was always in a fault state. Not allowing the elevator to move.

    The Debugging Steps where the following:
  • Identify the Fault State on the A12A100 Servo motor Contoller
  • Compare Configuration Against other controllers
  • Trace Back the "Limit" Switches wireing
  • Indetify if the elevator moves if we Disconnect The Limit Swicth from the Servo Controller
  • Find the Offset From the IR Light Detectors
  • Sync them in Place to exit the Fault State
  • Finally, Test the elevator with the fixed Elevator
